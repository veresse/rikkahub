# 应用更新流程

维护者推送到 `main` 后，`Build Custom Release APK` 自动编译、运行单元测试，通过后发布带递增版本号的 APK（先以草稿上传全部安装包，再公开）。自动同步作者代码先把合并结果放到 `sync/staging` 分支完成同样的构建、测试和发布，全部通过后才快进 `main`，流程与失败处理见 [upstream-sync.md](upstream-sync.md)。发布串行执行，版本和签名沿用现有配置。

GitHub 渠道应用启动、回到前台时检查更新；前台每小时复查，后台 WorkManager 每六小时按系统调度检查。首次配置未完成或用户暂停检查期间不提醒。后台检查受省电、网络、强行停止限制，不是即时推送。通知权限关闭时仍可使用前台提示和“设置 → 关于 → 检查更新”。

更新页自动选择设备 ABI。下载由系统 DownloadManager 执行，退出应用后仍可继续。回到更新页可继续查看下载或安装。前台下载完成自动打开安装步骤；后台下载完成发通知，用户点击后进入更新页安装。安装之前检查包名、版本和签名；系统仍要求用户确认覆盖安装。首次需要允许此应用安装未知来源应用。

Play 渠道不运行本更新流程，也不声明安装 APK 权限。

## 真机验收

1. 安装使用相同签名的较旧 GitHub APK，发布更高版本。启动或回前台应有更新提示。
2. 点稍后，再从“设置 → 关于 → 检查更新”打开，正确选择 arm64 或 x86_64 包。
3. 下载时分别拒绝和允许通知权限，均应可下载；拒绝权限时回更新页安装。
4. 前台完成下载，首次安装授权后返回，进入系统确认安装；覆盖后核对版本和聊天记录。
5. 后台完成下载，点击完成通知进入更新页；杀进程重开后下载仍可恢复。
6. 断网下载后恢复网络；失败时可重新下载。安装授权拒绝后仍有“安装更新”按钮。
7. 同版本不提醒；暂停检查期间不自动提醒；Play 渠道无更新提示和安装权限。

旧客户端如果更新地址已失效，需要手动覆盖安装一次过渡版本；云端发布不能修改手机中旧 APK 的代码。
